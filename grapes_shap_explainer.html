01

Your question comes in

Everything starts with a clinical query — a description of a real patient situation that needs a medical recommendation.

📥 What enters the system
Example patient query (raw text)
"70-year-old male, stage IIIB NSCLC, EGFR exon 19 deletion confirmed, ECOG PS 1,
 prior 4-cycle cisplatin/pemetrexed with progression, 3 asymptomatic brain metastases,
 PD-L1 TPS 15%. What is the optimal treatment strategy?"

This is just a string of text at this point. The system hasn't done anything with it yet. Think of it as the question on a doctor's desk before any research begins.

💡
Real-world analogy: This is like a junior doctor writing up a patient case and asking a senior consultant for advice. The senior consultant (our AI) needs to go find relevant research, think through options, simulate outcomes, and then explain their reasoning — not just guess.

Why it matters

The quality of the input determines everything downstream. A detailed clinical query (age, stage, mutation, prior treatments) gives the AI much more to work with than "what drug for lung cancer?"

Impact

More clinical context → more targeted document retrieval → more relevant outcome simulation → more specific final recommendation. Garbage in, garbage out.

02

Query expansion — 3 versions of your question

Before searching anything, we make the question smarter by generating 3 different versions of it. This dramatically improves what we find.

🧠 What happens inside

We create three representations of the query, each designed to find different kinds of relevant information:

Version 1 — Original query (captures clinical context)
query_original = "70-year-old male, stage IIIB NSCLC, EGFR exon 19 deletion..."
Version 2 — HyDE (Hypothetical Document Embedding) — LLM writes an ideal answer first
hypothetical_answer = "For EGFR exon 19 deletion NSCLC with prior platinum resistance and brain
  metastases, osimertinib 80mg daily is first-line per NCCN 2024 guidelines due to
  superior CNS penetration. 1-year OS 78-85% in real-world data..."

hyde_embedding = Encode(hypothetical_answer) ← this is now the search query!
Version 3 — Sub-query decomposition (atomic pieces)
sub_queries = [
  "EGFR exon 19 deletion treatment",
  "prior platinum resistance osimertinib",
  "brain metastases NSCLC CNS penetration"
]
💡
Real-world analogy: Imagine you're searching a library. If you only search the exact words of your question, you might miss the best books. So you also search: (1) what the answer to your question would look like, and (2) each individual topic separately. You cast a wider, smarter net.
Recall@6 with single query: 0.61 → With triple expansion: 0.87 (+43%)

Why HyDE works

Clinical queries ("70yr male, EGFR+") and clinical papers ("osimertinib efficacy in EGFR-mutant") use completely different vocabulary. HyDE bridges this gap by encoding an answer that already uses paper-style language.

Why sub-queries work

One complex query might match no single document perfectly. Three focused sub-queries each find their best matching document, and we combine results. More coverage, less missed evidence.

03

Hybrid retrieval — two search engines working together

We run two completely different types of search in parallel and combine results. Dense (semantic) + BM25 (keyword). Each finds things the other misses.

🔍 Dense search (semantic meaning)

Converts every document and query into a list of 384 numbers (a "vector"). Documents with similar meaning end up with similar numbers, even if they use different words. Uses FAISS HNSW — GPU-accelerated index for <5ms search over millions of documents.

How a document becomes a vector
"EGFR exon 19 deletion responds to osimertinib..."
↓ MiniLM-L6-v2 encoder ↓
vector = [0.23, -0.41, 0.87, 0.12, -0.33, ... 384 numbers total ...]

Similarity = dot product between query vector and document vector
score = 0.89 ← very relevant!
🔤 BM25 search (exact keyword matching)

Old-school text search that finds exact word matches. Critical for medical terms: "EGFR", "osimertinib", "T790M". Dense search might miss these exact names; BM25 catches them reliably.

BM25 scoring (simplified)
# Query contains "EGFR" and "osimertinib"
score_doc1 = 4.2 ← contains both terms + high IDF (rare = important)
score_doc2 = 1.8 ← only contains "EGFR"
score_doc3 = 0.3 ← neither term, general lung cancer article
⚖️ Reciprocal Rank Fusion — combining the two lists

Both searches return ranked lists. We combine them with RRF — a simple formula that rewards documents appearing highly in BOTH lists. No score normalisation needed.

RRF formula (k=60 prevents top-1 domination)
rrf_score(doc) = Σ 1 / (60 + rank)

Example: doc appears rank #1 in dense, rank #3 in BM25
score = 1/(60+1) + 1/(60+3) = 0.0164 + 0.0156 = 0.0320 ← top candidate!

Dense alone fails when

Query uses different vocabulary than the document. "osimertinib" vs "EGFR TKI third generation" — semantically related but lexically different. Dense catches this, BM25 might not.

BM25 alone fails when

Query uses synonyms or related concepts. "brain metastases" vs "CNS involvement" — BM25 misses this, dense catches it. Together they cover all cases.

04

Re-ranking + MMR — precision then diversity

We now have ~20 candidate documents from RRF. Two more filters: a precision filter (cross-encoder) and a diversity filter (MMR). Quality then variety.

🎯 Cross-encoder re-ranking (precision)

The RRF gives us top-20. Now we use a much more powerful (but slower) model that reads the query AND document together in one pass. It scores each pair with full attention. Runs on CPU to save GPU for the LLM.

How cross-encoder differs from bi-encoder (dense)
# Bi-encoder (dense): encode separately, then compare
query_vec = Encode("EGFR patient...") → [0.23, -0.41, ...]
doc_vec = Encode("osimertinib study...") → [0.19, -0.38, ...]
score = dot_product(query_vec, doc_vec) ← fast but approximate

# Cross-encoder: reads BOTH at once (sees full interaction)
score = CrossEncoder("EGFR patient... [SEP] osimertinib study...") ← slow but accurate
🌈 MMR — Maximum Marginal Relevance (diversity)

After re-ranking, the top-6 might all be about the same thing. MMR fixes this: it iteratively picks documents that are relevant but also different from what's already selected. λ=0.6 means "60% relevance, 40% novelty".

MMR in action — building our final top-6
Round 1: Pick most relevant doc overall
selected[0] = "FLAURA trial: osimertinib 80.7% ORR, 18.9mo PFS..."

Round 2: Next must be relevant AND different from selected[0]
candidate_A: relevance=0.91, similarity_to_selected=0.88 → MMR = 0.6×0.91 - 0.4×0.88 = 0.19
candidate_B: relevance=0.82, similarity_to_selected=0.23 → MMR = 0.6×0.82 - 0.4×0.23 = 0.40 ← wins!

Candidate B wins even though it's less relevant, because it adds new information!
Final top-6 documents selected (diverse coverage)
[1] "FLAURA trial: osimertinib PFS 18.9mo..." ← efficacy data
[2] "CNS penetration: intracranial ORR 91% with osimertinib..." ← brain mets
[3] "Cisplatin resistance mechanisms: ERCC1, Bcl-2..." ← resistance biology
[4] "Adverse events: dermatitis 58%, diarrhea 41%..." ← safety profile
[5] "EGFR T790M resistance after 1st gen TKIs..." ← resistance evolution
[6] "Real-world OS 78-85% at 1 year, age ≥70 safe..." ← real-world evidence

Without re-ranking

Fast vector search sometimes returns near-duplicate papers or slightly off-topic results. The cross-encoder catches these with full reading comprehension, boosting NDCG@6 from 0.71 to 0.85.

Without MMR

All 6 documents might be about FLAURA trial results. We'd miss brain metastasis data, safety data, and resistance mechanisms. MMR ensures the LLM gets a complete clinical picture.

05

Causal knowledge graph — the system knows cause and effect

Beyond retrieved documents, we have a structured map of medical knowledge: which drugs treat which conditions, what causes resistance, what improves survival. This is not just facts — it's causal relationships.

🌐 What a knowledge graph looks like

Nodes are medical entities. Edges are causal relationships with a strength score from 0 to 1.

Clinical KG — subset of 16 nodes and their edges
# Nodes (entities)
entities = ["EGFR_mutation", "Osimertinib", "Cisplatin_resistance",
           "CNS_metastasis", "T790M_resistance", "Overall_survival", ...]

# Edges (causal relationships with strength)
EGFR_mutation ──sensitises──(0.93)──→ Osimertinib
Osimertinib ──improves──(0.89)───→ Overall_survival
Osimertinib ──penetrates──(0.91)──→ CNS_metastasis
Cisplatin ──induces──(0.86)────→ Cisplatin_resistance
T790M_resistance ──overcomes──(0.82)──→ Osimertinib
Platinum_chemo ──causes──(0.66)─────→ Toxicity_G3
🧪 Graph Attention Network (GNN) — learning from the graph

A neural network runs over the relevant 1-hop subgraph. It learns richer node representations by attending to neighbours, weighted by causal strength. The key innovation: attention scores are biased by causal edge weights.

Edge-biased attention (standard attention + causal weight)
# Standard attention: how much should node u pay attention to node v?
α_uv = softmax( (Q_u · K_v) / √d ) ← learned from data

# Our innovation: also add the causal weight from the KG
α_uv = softmax( (Q_u · K_v) / √d + W_e · w_uv ) ← w_uv = causal strength

# Result: EGFR pays strong attention to Osimertinib (w=0.93)
# EGFR pays weak attention to Toxicity_G3 (w=0.0 — no direct edge)
Output: graph embedding vector (one rich number summary of the KG subgraph)
graph_emb = [0.34, -0.12, 0.78, 0.05, ... 384 numbers ...]
# Encodes: "this case is about EGFR+ NSCLC with brain mets and prior platinum resistance"
# This gets injected into the World Model to constrain its predictions!

Why not just use the documents?

Documents contain facts but not structured cause-effect relationships. The KG tells the system: "osimertinib CAUSES survival improvement via the EGFR pathway" — not just "they appear together in text".

Impact on World Model

The graph embedding constrains the World Model so it can't predict outcomes that violate known pharmacology. It's like giving the simulator a physics engine — it can't predict things that defy known cause-effect relationships.

06

Latent World Model — simulating the future

This is the most novel part. Instead of just finding relevant papers, we actually simulate what would happen to THIS patient under different treatments. Like a flight simulator, but for medicine.

🌍 What is a World Model?
✈️
Analogy: A flight simulator predicts "if pilot does X, plane responds Y" without actually flying. Our World Model predicts "if doctor gives treatment X, patient state changes to Y" — without waiting months for real outcomes.
Patient state — what the model tracks (24 clinical variables)
patient_state = {
  "vitals": [0.72, 0.45, 0.81], ← normalised HR, BP, temp
  "labs": [0.33, -0.12, 0.61], ← CEA, LFTs, creatinine
  "disease_state":[0.89, 0.23, 0.67], ← tumour markers, PS, stage
  ... 24 values total ...
} ← encoded to 384-dim latent vector z_t
⚙️ How the transition works (one timestep)
Step-by-step: patient state at time t → time t+1
1. Encode current state z_t (384 numbers)
2. Causal residual: how does THIS action shift the state given known pharmacology?
Δ_causal = MLP(z_t, action, graph_emb) ← informed by KG!

3. GRU dynamics: how does the state evolve over time?
z_next = GRU(z_t + Δ_causal, action_embedding)

4. Uncertainty: how confident are we in this prediction?
σ_uncertainty = Softplus(MLP(z_next)) ← bigger = less certain

5. Add small noise scaled by uncertainty (stochastic simulation)
z_next += random_noise × σ_uncertainty
Reward signal — how good was this action?
reward = -( side_effects(action) + guideline_deviation(action, KG) )
# Negative: we want to minimise harm and guideline violations
# Example: osimertinib has low reward penalty (aligned with guidelines)
# cisplatin re-challenge has high penalty (violates resistance KG edge)

Why simulate at all?

Without simulation, the AI can only say "papers suggest X is good." With simulation, it says "for THIS patient's specific state, X predicts 82% 1yr survival vs 61% for Y." That's actionable clinical precision.

The causal residual innovation

Standard world models are pure data-driven. Ours adds Δ_causal — a KG-informed correction that forces the simulation to respect known cause-effect relationships even in out-of-distribution scenarios.

07

Tree-of-Thought planning — finding the best treatment path

Now we test multiple treatments by simulating each one into the future, then pick the best. Like a chess engine that thinks 5 moves ahead for 8 different openings, then chooses the best.

🗺️ How ToT planning works (step by step)
Planning loop — M=8 candidates × H=5 steps ahead
# For each of 8 candidate first actions (treatments)...
candidates = [osimertinib, chemo, immunotherapy, osim+chemo, radiation, ...]

For candidate "osimertinib":
  step1: state_t0 → give_osimertinib → state_t1 (reward: +0.82)
  step2: state_t1 → monitor+dose → state_t2 (reward: +0.71)
  step3: state_t2 → continue → state_t3 (reward: +0.68)
  step4: state_t3 → monitor → state_t4 (reward: +0.65)
  step5: state_t4 → adjust → state_t5 (reward: +0.61)
  final_state = state_t5

For candidate "cisplatin re-challenge":
  step1: state_t0 → give_cisplatin → state_t1 (reward: -0.43) ← KG says resistance!
  ... (trajectory is bad from step 1)
🏆 Scoring each candidate path
Composite score formula
score = V(z_final) ← long-term outcome value from ensemble
        + 0.5 × sum(all_rewards) ← step-by-step reward
        - 0.1 × mean(uncertainty) ← penalise risky/uncertain paths

Results:
osimertinib: score = +3.47 ← WINNER
osim + carboplatin: score = +2.91
immunotherapy alone: score = +1.23 ← low (EGFR+ poor ICI response)
cisplatin re-challenge: score = -0.82 ← penalised by KG
Best plan selected
best_actions = [osimertinib_80mg, monitor_4wk, dose_check, continue, CNS_surveillance]
best_score = 3.47

vs simple recommendation

A simple RAG system says "papers show osimertinib is good." ToT planning says "I simulated 8 treatment paths 5 steps into the future and osimertinib scores 3.47 vs 1.23 for immunotherapy for THIS specific patient." Much stronger evidence.

The uncertainty penalty

If the world model is very uncertain about a path, we discount it. This prevents the system from choosing a path that looks great but is actually a guess. Safety over optimism.

08

Deep Ensemble — uncertainty quantification

Five independent neural networks predict the outcomes. Their agreement tells us how confident to be. We split uncertainty into two types: "we don't know yet" vs "it's genuinely unpredictable".

🎲 Why 5 models instead of 1?
🧑‍⚕️
Analogy: Ask 5 independent oncologists the same question. If they all agree the prognosis is 80-85% survival, you can be confident. If they disagree (60%, 75%, 90%, 82%, 70%), the uncertainty is high and you should be more cautious about the recommendation.
5 ensemble members predict 5 clinical outcomes
Each member is a different neural network trained independently:

             member_1 member_2 member_3 member_4 member_5
1yr survival: [0.831, 0.819, 0.843, 0.827, 0.836]
readmission: [0.178, 0.201, 0.167, 0.183, 0.175]
complication: [0.142, 0.158, 0.137, 0.149, 0.143]
📏 Two types of uncertainty (very important distinction)
Decomposing uncertainty
# Mean prediction
μ_survival = mean([0.831, 0.819, 0.843, 0.827, 0.836]) = 0.831

# Epistemic uncertainty: models DISAGREE → we need more data
σ_epistemic = std(means) = 0.009 ← small! models agree

# Aleatoric uncertainty: inherent randomness in medicine
σ_aleatoric = mean(std_within_each_model) = 0.024 ← patient biology is variable

# Total uncertainty
σ_total = √(σ_epistemic² + σ_aleatoric²) = 0.026

# Final output:
"1-year survival: 83.1% ± 2.6%"
📊 All 5 outcome predictions
1-year survival83.1% ± 2.6%
30-day readmission risk18.2% ± 3.1%
Complication rate14.6% ± 2.1%
Toxicity score0.32 ± 0.04
PFS at 1 year76.4% ± 3.0%

Why this matters clinically

"83% survival" sounds confident. "83% ± 26% survival" is alarming. "83% ± 2.6% survival" is trustworthy. The ± tells the doctor whether to trust the number or seek more information first.

Epistemic vs aleatoric

High epistemic uncertainty → collect more data (this patient is unusual). High aleatoric uncertainty → the outcome is inherently variable (some patients respond, some don't). Different clinical actions needed for each.

09

LLM reasoning — writing the actual answer

Now all the pieces come together. The LLM (Mistral-7B) reads everything collected so far and writes a structured clinical recommendation with chain-of-thought reasoning.

⚡ What gets fed to the LLM
Complete structured prompt (simplified)
PATIENT: "70yr male, stage IIIB NSCLC, EGFR exon 19 del, prior cisplatin..."

EVIDENCE (6 retrieved documents):
  [1] "FLAURA trial: osimertinib PFS 18.9mo vs 10.2mo..."
  [2] "CNS penetration: intracranial ORR 91%..."
  [3] "Cisplatin resistance: ERCC1 upregulation..."
  ... 3 more ...

SIMULATION RESULT: Best plan = osimertinib path, score=3.47
PREDICTED OUTCOMES: survival=83.1%±2.6%, readmission=18.2%±3.1%, ...

TASK: "Provide: (1) chain-of-thought reasoning citing evidence numbers,
         (2) specific treatment recommendation,
         (3) risk-benefit summary, (4) follow-up protocol"
🔧 Why 4-bit compression (QLoRA)?

Mistral-7B has 7 billion parameters. At normal 32-bit precision that's 28GB — won't fit on a 24GB GPU. We compress each parameter to 4 bits using NF4 (NormalFloat4), keeping quality while reducing to 6.5GB.

Memory comparison
full_precision_32bit: 7B × 4 bytes = 28 GB ← won't fit on RTX 4090
half_precision_16bit: 7B × 2 bytes = 14 GB ← fits but tight
nf4_4bit: 7B × 0.5 bytes = 3.5 GB ← comfortable!
with_lora_adapters: 3.5 + 3.0 GB = 6.5 GB total used
LoRA — fine-tune with only 0.7% of parameters
# Original weight matrix (frozen):
W_original: 4096 × 4096 = 16.7M params ← DO NOT CHANGE

# LoRA adds two tiny matrices (trainable):
A: 4096 × 16 = 65k params
B: 16 × 4096 = 65k params
ΔW = A × B ← only train these! (130k vs 16.7M = 0.8%)

Why Flash Attention 2?

Standard attention computes a huge N×N matrix (tokens × tokens). With a 2048-token prompt that's 4 million entries. Flash Attention 2 recomputes on-the-fly using memory tiles, using O(n) memory instead of O(n²). 2-3× faster, much less VRAM.

Why chain-of-thought?

Asking the LLM to reason step-by-step ("cite evidence [1], then consider [3]...") forces it to explicitly use the retrieved documents rather than hallucinate. Improves accuracy and makes the reasoning auditable.

10

Hallucination detection — fact-checking the answer

LLMs sometimes invent plausible-sounding but false medical facts. We run two independent checks to catch this. Any flagged claim is highlighted for the clinician to review.

Layer 1 — Self-RAG (happens DURING generation)

The LLM is trained to insert special "critique tokens" as it writes. These are internal checkpoints that trigger re-retrieval if confidence is low.

Critique tokens in action
"Based on evidence [1], osimertinib is recommended..." [IsREL=YES] [IsSUP=fully]
"The 2-year survival rate is approximately 92%..." [IsREL=YES] [IsSUP=partial]

→ IsSUP=partial triggers: re-retrieve more evidence about 2-year survival
→ After re-retrieval: "real-world data shows 55-65% 2-year OS"
→ LLM regenerates that sentence with the correct figure
Layer 2 — NLI verification (happens AFTER generation)

After the full answer is written, we extract every claim and check it against retrieved documents using Natural Language Inference (NLI) — a model trained to detect contradiction, neutral, or entailment.

NLI checking each sentence
# Claim 1:
claim: "Osimertinib shows 80.7% objective response rate"
evidence: "FLAURA trial: ORR 80.7%..."
NLI_result: ENTAILMENT ✓ supported

# Claim 2 (hallucinated):
claim: "Cisplatin can be used as second-line after resistance develops"
evidence: "Cisplatin resistance involves ERCC1 upregulation..."
NLI_result: CONTRADICT ⚠ flagged for clinician review
Final hallucination report
factual_grounding_score: 0.91 ← 91% of claims supported
flagged_claims: 1 ← highlighted for clinician
supported_claims: 11 ← all entailed by retrieved evidence

Hallucination rate comparison

SystemHalluc. rate
Basic RAG+LLM18.4%
+ NLI only12.1%
+ Self-RAG only10.8%
GRAPES-SHAP dual7.9%

Why two layers, not one?

Self-RAG catches hallucinations during writing (proactive). NLI catches ones that slipped through (reactive). Like a spell-checker while you type AND a proofreader when you're done. The two layers together cut errors by 57% vs none.

11

SHAP attribution — explaining which evidence drove the answer

Which of the 6 retrieved documents actually mattered? We use game theory (Shapley values) to fairly measure each document's contribution. This makes the AI's reasoning transparent and auditable.

🎮 Shapley values — game theory explains AI
⚽
Analogy: A football team wins 5 games. How much did each player contribute? Shapley values answer this by asking: "how much better is the team WITH vs WITHOUT this player, averaged over all possible team compositions?" Fair, mathematically proven, not just attention scores.
Computing Shapley value for Document [1] (FLAURA trial)
# Run 32 random permutations of the 6 documents
# Each time: what's the model score WITH vs WITHOUT doc[1]?

Permutation 1: {doc3, doc5, [doc1], doc4, doc2, doc6}
score_before_adding_doc1: 0.41 (only docs 3 and 5 present)
score_after_adding_doc1: 0.67 (added doc 1)
marginal_contribution: +0.26

Repeat 32 times, average the marginal contributions
φ_doc1 = mean(all_marginals) = 0.312 ← highest SHAP value!
📊 SHAP scores for all 6 documents
[1] FLAURA trial — osimertinib efficacy φ = +0.312
Drove the recommendation: "use osimertinib" directly supported by ORR/PFS data
[2] CNS penetration — brain mets data φ = +0.248
Critical for this case: patient has brain metastases; intracranial ORR 91% sealed the choice
[3] Cisplatin resistance mechanisms φ = +0.187
Explained why cisplatin re-challenge was rejected; ERCC1 resistance pathway confirmed
[4–6] Safety, T790M, real-world data φ = 0.04–0.09
Supporting context but not driving the core recommendation
🔗 Pairwise interaction effects (novel contribution)

Some documents work better together than alone. Interaction effects reveal these synergies — a feature not found in other RAG interpretability systems.

Interaction formula: I(i,j) = f({i,j}) - f({i}) - f({j}) + f({})
# Doc[1] alone contributes +0.312
# Doc[2] alone contributes +0.248
# Together they contribute +0.71 (vs expected +0.56)
interaction_1_2 = 0.71 - 0.312 - 0.248 + 0.0 = +0.15 synergistic!

# Why? Docs [1]+[2] together form the complete argument:
# "osimertinib works" + "AND it works in the brain" = compelling case for THIS patient
